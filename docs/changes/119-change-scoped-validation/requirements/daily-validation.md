# 日常验证与完整回归

## 客户目标与场景

开发者更新一个功能后，应及时得到与本次改动有关的验证结果。修正文档、局部业务逻辑和共享能力时，检查范围应不同；进入提交或交付阶段不应重复已经充分完成的检查。

## 范围与约束

- 提供日常验证入口、完整验证入口、CI 分流及清晰的执行证据。
- 必须覆盖受影响的使用方，不能靠少跑必要检查换取速度；已失败的检查必须保持失败可见。
- 本地没有可比较历史时，明确说明扩大验证，不能报告“无改动”。
- 不改变业务功能、数据、生产部署和视觉基线，不引入新的大型任务平台。
- 不承诺固定提速比例；首次整库导入、依赖变动和发布验证仍可能较慢。

## 可验收行为

- REQ-119-001：纯文档改动不触发应用编译、业务单测或浏览器安装，仅执行适用文档验证。
- REQ-119-002：局部后端更新验证所属范围及受影响调用方，不默认对全仓执行两遍非缓存测试；并发相关更新保留相应竞争检测。
- REQ-119-003：局部前端更新执行必要治理、静态检查、类型和相关测试，不默认执行全站生产构建、性能预算与全部浏览器场景。
- REQ-119-004：共享契约、依赖或验证工具自身更新时明确扩大范围并解释原因；提供完整回归的显式入口。
- REQ-119-005：每次输出检查原因、执行范围、成功/失败及耗时；未运行项不能描述为通过。
- REQ-119-006：同一代码状态已通过的适用检查不因阶段切换重复执行；新增相关修改、失败或证据缺口才触发重验。
- REQ-119-007：CI 能区分前端、后端与文档更新，保留多平台完整回归和发布门禁；相同 PR 被新提交取代的检查可取消。
