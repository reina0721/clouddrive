# 生产编译持久缓存的定向复核

## 事实与问题

本批主与QA分别使用独立生产目录。磁盘空间不足曾导致Go链接失败；空间恢复后Go全量与vet通过，但最后的主前端构建仍报告缓存压缩失败。旧构建目录删除操作被自动审批拒绝，未改用其他删除手段。

当前安装的官方Next16.4.5源码中，config-shared.js默认启用turbopackFileSystemCacheForBuild；turbopack-build/impl.js把该选项交给persistentCaching。它控制编译数据库复用，不是应用数据、鉴权、页面加载缓存或代码优化开关。关闭后仍使用同一编译器及Next Runtime。

## 决策、影响与验证边界

在现有next.config.ts集中关闭生产构建持久缓存。只影响后续构建的增量复用成本；不清理既有目录，不修改开发缓存，不增加隐藏环境变量或新的编译入口，也不放宽原首屏、路由、CSS及PDF资源预算。

这是当前已授权交付中的构建资源修正，没有改变20项用户功能、公共接口、依赖或模块边界。完整构建、原性能门禁与最终运行验证仍是完成条件；不能仅凭关闭配置就宣称产物通过。Next升级或建设共享构建缓存时重新评估空间与构建时间。

后续证据：最终主/QA构建均退出0，无缓存压缩警告，原体积预算通过。恢复临时空间时使用Windows NTFS无损压缩处理已停用生成目录，保留所有文件；遇到文件锁即停止该目录，不绕过锁。具体操作与成功目录保存在ignored `.data/135-lossless-build-compression.log`。原数据库及正在使用的生产目录未参与该操作。
